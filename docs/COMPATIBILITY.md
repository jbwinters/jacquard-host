# Compatibility

## Pinned Core release

Every adapter in this repository is pinned to one published Jacquard Core
release, recorded once in [`core-pin.json`](../core-pin.json). The Python
constants (`src/jacquard_host/compat.py`), the TypeScript constants
(`typescript/src/compat.ts`), the Go constants (`go/protocol/compat.go`), the
Rust constants (`rust/src/compat.rs`), the Java constants
(`java/src/main/java/org/jacquardlang/host/Compat.java`), the .NET constants
(`dotnet/src/JacquardHost/Compat.cs`), and the block below are generated from
that file by `scripts/core_pin.py sync`.
`scripts/core_pin.py check` fails CI when any of them drifts from the pin. It
also fails when any vendored kit copy drifts: the Python package data, Go's
embedded `go/kit/data/`, the Rust crate's embedded `rust/kit/`, the Java
class-path copy under `java/src/main/resources/`, or the .NET embedded copy
under `dotnet/src/JacquardHost/kit/`. Adapters verify the kit's four
digests independently at load time, and the SDKs refuse a Core whose
`--version` differs from the pinned version.

Python, TypeScript, Go, Rust, Java, and .NET replay the same 21 recordings against the pinned
worker, including Core's recorded `noncanonical-target-hash` divergence: the
HB.1 vector expects E1603 while the shipped preflight classifies an uppercase
target hash as a malformed scalar (E1601). The transcript is recorded as
`diverges`, and the adapters reproduce that recording rather than hiding it.
Diagnostic prose is not normative and is reported, never normalised. This is
independent v0 evidence; it does not change the protocol version or declare v1.

The adapters decode boundary descriptors in Core's order: the kind, then the
exact fields, then one node of `max_value_nodes`, then any identity, then the
list count. Malformed input therefore gets the same error code from every
adapter and from Core. For recording comparisons, Python, Go, Rust, Java, and .NET sort
object keys by code point, while TypeScript sorts them by UTF-16 code unit. The two orders
differ only for keys outside the Basic Multilingual Plane. Every protocol key is
ASCII, so the comparisons agree.

## Status of the pin

Releases from `jacquard-core-0.3.0` publish checksummed binaries that include
the host worker and the matching prelude, so the pin names a release tag
rather than a development commit. `scripts/core_pin.py install` downloads the
asset for this platform, verifies its SHA-256 against the pin, and prints the
`JACQUARD_BIN` and `JACQUARD_PRELUDE` to export; [SETUP.md](SETUP.md) also
describes a source build of the same tag for other platforms. Keep the
executable and prelude from the same release.

The host-protocol kit is unchanged between the earlier development pin (Core
`main` at `61575c7`, which reported version 0.2.0 although the 0.2.0 release
predates the worker) and `jacquard-core-0.3.0`, except for the `core_version`
it records.
Core owns a "stable v1" decision and its acceptance of the independent
adapter and serial-application evidence; these implementations still select v0.

## Adoption rule

Implementation of an adapter begins only after `jacquard-lang` publishes all
of the following together:

1. a versioned, transport-neutral host contract;
2. a concrete carrier version;
3. canonical positive and hostile conformance fixtures;
4. explicit bounds and unknown-input behavior; and
5. an evidence and limitations statement.

All five items are satisfied by the pinned specification, worker, kit, and
evidence pack at the pinned release. Adapter-specific normalization
may not weaken, repair, or silently reinterpret a fixture. Protocol divergence
is reported upstream or fixed in the adapter; it is never hidden behind a
language-specific compatibility rule.

The process carrier is expected to be provisional. A later native or
WebAssembly carrier may replace it while preserving the transport-neutral
invocation, effect, diagnostic, cancellation, and evidence contract.

## Following Core releases

Check whether Core has published a newer release:

```sh
python3 scripts/core_pin.py status   # exit 3 when a newer release exists
```

Adopt a release in its own pull request:

```sh
python3 scripts/core_pin.py update --tag jacquard-core-X.Y.Z
# or, offline for the kit: --core-checkout /path/to/jacquard-lang
eval "$(python3 scripts/core_pin.py install)"
PYTHONPATH=src python3 -m unittest discover -s tests -v
python3 -m pip install . && python3 scripts/check_examples.py
(cd typescript && npm ci && npm test && npm run test:live && npm run check:package)
(cd go && go test -race ./... && go test -count=1 ./...)
(cd rust && cargo test)
(cd java && JACQUARD_REQUIRE_LIVE=1 mvn -B verify)
(cd dotnet && JACQUARD_REQUIRE_LIVE=1 dotnet test test/JacquardHost.Tests -f net8.0)
```

`update` resolves the tag to its commit, copies the kit files from
`spec/host-protocol-v0/` at that commit, records their digests and the
release's checksummed assets, and regenerates every adapter's constants. It
refuses a release whose kit names a different protocol or carrier: that is
adapter work, not a pin refresh. CI then installs the new release and runs both
adapters' live suites and the public examples against it.

A transcript that stops matching its recording, or an SDK preparation that
changes behavior, is a protocol or implementation finding to report upstream,
not something to normalise here. Record the adoption and its evidence in
[EVIDENCE.md](EVIDENCE.md) and the [changelog](../CHANGELOG.md).
