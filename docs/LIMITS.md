# Limits

These are claim boundaries for the first host integration, not background
aspirations. Evidence may remove a limit only through a reviewed change that
also updates this document.

| Initial limit | Consequence | Evidence required to remove it |
|---|---|---|
| First-party Jacquard programs only | Capability checks do not make hostile uploaded code safe. | A separate-process or equivalent isolation design, adversarial review, resource ceilings, and a narrower public threat model. |
| Trusted host and operating system | A malicious or buggy adapter can misreport or perform actions outside Jacquard. | An authenticated, independently enforced host boundary and external security review; canonical hashes alone are insufficient. |
| Application capability boundary, not OS sandbox | Declared and checked effects are review and application enforcement, not kernel isolation. | An explicit OS/WebAssembly/container isolation layer with its own evidence and deployment contract. |
| Experimental process carrier (Core's `v0`, evidence pack published) | Message framing may change and is not a permanent ABI promise; Python, TypeScript, Go, Rust, Java, and .NET replay the pinned kit independently, while a stable protocol decision remains Core's. | Two independent adapters and the serial application pass the same frozen fixtures before Core declares protocol v1 stable. |
| Handlers run inside the adapter's read loop | A Python operation handler that blocks holds the worker until it returns. The host deadline is one lifetime budget from spawn, enforced on pipe reads, writes, and exit waits; a slow handler spends the budget and the next carrier operation expires. It cannot interrupt Python handler code. | A handler timeout policy with its own cancel/unknown-completion evidence, once an application needs one. |
| Go worker descendants that leave the process group | The Go host stops the worker's process group at expiry, and on Linux also after exit while a descendant still holds stderr; elsewhere, and for a descendant that called `setsid` (or otherwise left the group), it only stops reading the pipe. | An OS-level containment mechanism (for example a cgroup or job object) with its own evidence. |
| Go handler cancellation is cooperative | At the deadline or on context cancellation the Go host kills the worker's process group (while the worker is unreaped, which Linux guarantees), closes its pipes, and reaps it, cancels the handler's context, and sends no late response; a handler that ignores its context keeps running in its goroutine until it returns. No outside action is stopped or rolled back. | A separately enforced operation lifetime with explicit completion and reconciliation evidence. |
| Rust worker descendants that leave the process group | The Rust host stops the worker's process group at expiry. On Linux it also stops the group after exit while a descendant still holds stderr, because `waitid(WNOWAIT)` keeps the leader unreaped. Elsewhere, and for a descendant that left the group, it stops waiting once the grace or the lifetime deadline ends. On Unix its pipe threads then stop within one poll interval and the pipes are closed, but the descendant keeps running. Non-Unix targets only type-check: their pipe I/O cannot be interrupted, so disposal can hang while a descendant holds a pipe, and the offline stand-in, and so the offline suite, is Unix-only. | An OS-level containment mechanism (for example a cgroup or job object) with its own evidence. |
| Rust handler cancellation is cooperative | Each Rust handler runs on its own thread. At the deadline or on cancellation the host kills the worker's process group, closes its pipes, reaps it, and sends no late response; `HandlerContext::is_cancelled` turns true, and stays true once the invocation ends. A handler that ignores it keeps running on its thread until it returns. No outside action is stopped or rolled back. | A separately enforced operation lifetime with explicit completion and reconciliation evidence. |
| Rust SDK field order is declared, not exported | `record!` and `variants!` list fields in the order the Rust code declares; the pinned CLI exports no field types, so a wrong order is not detected locally, and Core refuses it only where the swapped fields' types differ. | Core's structured host interface exporter, so bindings can be generated or checked. |
| Rust SDK preparation is not cancellable | Each Core `--version`, `check`, `hash`, and `run` command runs in its own process group with a 30-second timeout and bounded output; `prepare` takes no `Cancel`. On Linux the group is also stopped when the command exits. A descendant that left the group, or on other platforms any descendant, that keeps Core's output open fails preparation after a one-second grace and keeps running; on Unix the reader threads stop and the pipes close, while on non-Unix targets a reader blocked on such a pipe stays until the descendant closes it. | A cancellable preparation API, once an application needs one. |
| Java worker process tree, not group | The JDK cannot start the worker in its own process group, and the worker is not launched through `setsid` as the SDK's Core commands are on Linux, so the Java host kills a process tree. At expiry, cancellation, or disposal of a running worker, it snapshots `Process.descendants()` and kills the worker and every process in the snapshot. A descendant that was already reparented keeps running: one whose parent exited, or one that daemonized. So does one started after the snapshot. The JDK reaps the worker as soon as it exits. So stdout ends once the worker has exited and its pipe is empty, rather than when the worker closes it, and a descendant still holding a pipe after the exit is neither detected nor stopped. The Go and Rust hosts report a descendant holding stderr after a successful exit as a carrier loss; the Java host reports the worker's own result. The JDK reports a signal as exit status 128 + its number, so only the host's own SIGKILL is reported as a signal. | An OS-level containment mechanism (for example a cgroup or job object) with its own evidence, or a JDK process-group API. |
| Java pipe I/O cannot be interrupted | On Unix the Java host creates the worker's stdout and stderr as FIFOs (it needs `mkfifo`) and holds their read ends itself, because the JDK's own process pipes drain on its reaper thread at exit, under the lock `available()` takes and into an unbounded buffer, for as long as a descendant writes. On other systems it uses the JDK's pipes, so a descendant that keeps writing after the worker exits holds the caller, and grows the heap, until it stops. The Java host never blocks on a read. It reads stdout and stderr on the caller's thread only after `available()` reports bytes, in polls of 0.1 to 5 ms that recheck the deadline, the `Cancel`, and the interrupt status. Writes run on one stdin thread in chunks of at most 4096 bytes. Each chunk starts only while input is open, the lifetime is live, and the caller is not interrupted; a chunk already started may complete, and reach the worker, until the caller's next poll kills it (at most 5 ms after a cancellation). A descendant that escaped the kill may hold the stdin pipe without reading. Then a blocked write, or the flush and close that end the thread, keeps the stdin thread, and the JDK's process reaper thread for that worker, until the descendant exits or reads. The caller still returns at the deadline. | A JDK API for interruptible or non-blocking process pipes, or a carrier that does not use process pipes. |
| Java handler cancellation is cooperative | Each Java handler runs on its own daemon thread. At the deadline, on cancellation, or when the calling thread is interrupted, the host kills the worker's process tree, closes its input, and sends no late response. `HandlerContext.isCancelled` turns true, and stays true once the invocation ends. A handler that ignores it keeps running on its thread until it returns. No outside action is stopped or rolled back. | A separately enforced operation lifetime with explicit completion and reconciliation evidence. |
| Java SDK Core command descendants | Each Core `--version`, `check`, `hash`, and `run` command must exit within 30 seconds and keeps at most 8 MiB of stdout and 4 KiB of stderr; a `Cancel` or the caller's interrupt stops it. Its output goes through host-owned FIFOs on Unix. On Linux with a `setsid` at `/usr/bin/setsid` or `/bin/setsid` (util-linux's, or a compatible one such as BusyBox's; any executable there is used), the command runs as `setsid -- <core>`, which execs without forking, so Core keeps its pid and leads its own process group; when `setsid` cannot exec Core (exit status 126 or 127 with its own `setsid: ` message) the command is reported as a start failure. When the command exits, and on a timeout, cancellation, or interrupt, the host kills that group: it acquires each `/proc` process's `ProcessHandle`, then reads its group id from `/proc/<pid>/stat`, and kills it through that handle only on a match, so a pid reused after the handle was acquired is not killed. A match proves membership unless the group id was reused after the group emptied: after a full pid wraparound, a process that took Core's pid, made its own group, forked, and exited can have its child killed by a pass still running, the same window as the Rust SDK's `kill(-pgid)`. Under a JVM that is a child subreaper, a killed descendant reparented to the JVM stays its zombie, because the JDK reaps only its own children. A descendant that leaves the group (calls `setsid`) is neither detected nor killed; the Rust SDK detects one that holds Core's output ("its output did not close") but does not kill it, and the Java host, which holds its FIFOs read-write, cannot see EOF to detect it. A group id cannot be reused while the group has members, so once Core has been reaped, a live process holding Core's pid means the group is gone, and the pass stops without killing anything more. Without `setsid` (macOS, or Linux without one at those paths), descendants are recorded about every 10 ms by pid and start time, every recorded descendant still alive with that start time is killed when the command returns, and a stop also kills a snapshot of the process tree; that fallback misses fast fork-and-exit chains, and the host closes its ends after the exit, so a descendant still holding the output fails its next write. On non-Unix systems the JDK's pipes are used, so a descendant that keeps writing after the exit holds the caller, and grows the heap, until it stops. The Java worker does not run in its own group (see the worker row above). | An OS-level containment mechanism, or a JDK process-group API, with its own evidence. |
| Java SDK cache and source reads | A cache entry is verified against the file digests in its `program.json`, and every binding is derived again from Core's cached raw output, so an accidental or partial change is refused. No record inside the cache resists someone who can rewrite it: an output, its recorded digest, and the bindings changed together load. So the cache's owner is trusted and only the owner may write it: on POSIX file systems, preparation refuses a cache root, an entry, or any file or directory in one that the current user does not own or that its group or others may write, on create and on load, and new entries are owner-only. A symbolic link to the cache root is followed once and the real directory checked; nothing inside it is followed, and the cache root's parent directories are not checked. Without POSIX permissions (Windows) nothing is. A failed preparation's cleanup removes at most 100,000 entries of its staging directory and ends at a `Cancel` or interrupt, so a stopped preparation leaves an unpublished `prepare-*` directory in the cache root; it is never loaded, and nothing removes it later (a name and an age cannot show that the SDK made a directory or that no preparation is using it), so remove leftovers yourself when no preparation is running. At most 1,024 sources are taken, refused from the list's size before any element is read, and they must be regular files totalling at most 16 MiB, the Core executable at most 512 MiB, and the prelude and cache walks read at most 100,000 entries and 256 MiB of regular files under one root, each file checked from its size before it is read and again while it is read; a source replaced by a FIFO between that check and its open can still block the open, which neither a `Cancel` nor an interrupt ends. | An open that cannot block on a FIFO. |
| Java SDK signature depth | A checked function whose signature nests types deeper than 64 levels (`max_json_depth`, the protocol's value-depth limit), names more than 4,096 types, or has more than 16,384 tokens is left unbound, like a polymorphic one: preparation succeeds, the other functions bind, and binding it fails with a `BINDING` exception naming the limit. The SDK parses no operation signatures (Core's `check --print-sigs` prints none). | None needed for depth, since a deeper value cannot cross the protocol; Core's structured host interface exporter for the rest. |
| Java SDK record order is declared, not exported | A record's components, in declaration order, are a constructor's fields; the pinned CLI exports no field types, so a wrong order is not detected locally, and Core refuses it only where the swapped fields' types differ. | Core's structured host interface exporter, so bindings can be generated or checked. |
| Java fulfillment is a single-process snapshot example | Atomic JSON replacement demonstrates booking/outbox recovery and deduplication, without cross-process locking or power-loss durability evidence. | A concrete production storage contract and crash/concurrent-writer evidence. |
| Java platforms | Linux runs in CI. macOS has no CI; the offline descendant and fake-Core tests need `sh` and `sleep`, and the descriptor tests need `/proc`. Windows is not claimed. | CI, lifecycle, and cleanup evidence on each added platform. |
| .NET worker process tree, not group | .NET cannot start the worker in its own process group, so the .NET host kills a process tree. At expiry, cancellation, or disposal of a running worker, it calls `Process.Kill(true)`, which stops the worker, lists its children from the process table, kills it, and does the same for each child. A descendant that was already reparented keeps running: one whose parent exited, or one that daemonized. So does one started after its parent was listed. Descendants are found and signalled by pid, with nothing pinning their identity: one that exits, and is reaped once the worker is killed, between the listing and the signal can have its pid reused by an unrelated process, which is then signalled (the Java host signals process handles, and the Rust and Go hosts a process group). Listing the process table takes time proportional to the number of processes on the machine. The runtime reaps the worker as soon as it exits. A descendant still holding stdout or stderr after the exit is detected and, after a one-second grace, reported as a carrier loss, as the Go and Rust hosts report it; it is not stopped. .NET reports a signal as exit status 128 + its number, so only the host's own SIGKILL is reported as a signal. | An OS-level containment mechanism (for example a cgroup or job object) with its own evidence, or a .NET process-group API. |
| .NET pipe I/O goes through `poll(2)` | .NET's pipe streams have no read or write that a deadline or a cancellation can interrupt, so the .NET host never calls one that can block: the caller's thread asks the C library's `poll(2)` whether a pipe is ready, with a poll timeout of at most 5 ms, rechecking the deadline, the `CancellationToken`, and disposal between polls, and then reads only bytes already in the pipe or writes at most `PIPE_BUF` bytes (4096 on Linux, 512 on macOS), which a writable pipe accepts at once. No thread is left blocked on a worker pipe, even while an escaped descendant holds stdin without reading or floods stdout or stderr. The `pollfd` layout and event bits are the same on Linux and macOS; elsewhere, including Windows, the host does not start a worker and reports a spawn failure. .NET opens its own descriptors close-on-exec, but passes the worker any descriptor the host process itself inherited without that flag. | A .NET API for interruptible or non-blocking process pipes, and CI on each added platform. |
| .NET handler cancellation is cooperative | Each .NET handler runs on its own background thread. At the deadline or on cancellation the host kills the worker's process tree, closes its input, and sends no late response. `HandlerContext.IsCancelled` turns true (it reads the deadline exactly), and stays true once the invocation ends. `HandlerContext.CancellationToken` is cancelled when the call stops or ends, never earlier (a lifetime of any length does not cancel it before its deadline). While a handler runs, the caller's thread rechecks the deadline and the caller's token between poll waits of at most 5 ms; that is the requested poll timeout, not a bound on the interval between checks, which reading pending stderr (up to 1 MiB per pass) and thread scheduling can lengthen. Whichever check sees the stop, the token's cancellation starts before the worker is killed; otherwise it starts shortly after the invocation ends. The cancellation runs on a short-lived thread the host starts for it, one per invocation that gave a handler a token, so it does not wait for the shared thread pool. If no thread can be created or started, the host queues it as a pool work item, which runs only when a pool thread is free, so a starved pool delays it. If the work item cannot be queued either, the host gives up: the token is never cancelled (`HandlerContext.IsCancelled` still turns true), `InvocationResult.HandlerTokenNotCancelled` is set, and a handler waiting only on the token keeps waiting; `Invoke` still returns its result and disposes the worker. Callbacks a handler registers on that token run on that thread, which the host never waits for; a callback that blocks holds that thread, and anything a callback throws is discarded. A callback registered after the token is cancelled runs at once on the handler's own thread and throws there, as with any `CancellationToken`. A handler that ignores both keeps running on its thread until it returns. No outside action is stopped or rolled back. A stack overflow in a handler ends the process, as it does any .NET code. | A separately enforced operation lifetime with explicit completion and reconciliation evidence. |
| .NET SDK Core command descendants | Each Core `--version`, `check`, `hash`, and `run` command must exit within 30 seconds and keeps at most 8 MiB of stdout and 4 KiB of stderr; cancelling the token stops it. Its output is read only after `poll(2)` reports it ready, on the caller's thread. On Linux with a `setsid` at `/usr/bin/setsid` or `/bin/setsid` (util-linux's, or a compatible one such as BusyBox's; any executable there is used), the command runs as `setsid -- <core>`, which execs without forking, so Core keeps its pid and leads its own process group; when `setsid` cannot exec Core (exit status 126 or 127 with its own `setsid: ` message) the command is reported as a start failure. When the command exits, and on a timeout or cancellation, the host sends `kill(-pgid, SIGKILL)` to that group. Once .NET has reaped Core, a live process holding Core's pid means the id was reused and nothing is killed; a process that took Core's pid after a full pid wraparound, made its own group, and forked between that check and the kill could still have that group killed, the same window as the Rust SDK's `kill(-pgid)`. A descendant that leaves the group (calls `setsid`) is neither detected nor killed; the host does not wait for the end of the output after the exit, and closes its ends, so that descendant's next write fails. With `setsid`, the wait for a killed Core to exit after a stop ends 750 ms after the stop. Without `setsid` (Linux without one at those paths), descendants are recorded from `/proc` about every 10 ms by pid and start time, and every recorded descendant still alive with that start time is killed when the command returns (the start time is read just before the kill, a short window in which a reused pid could be signalled, as with the JDK's process handles). Each record reads at most 16,384 `/proc` entries and 4 MiB of `stat` files in all, each read limited to 1 KiB and to the bytes left, at most 16,384 descendants are kept, and a record ends at the deadline or a cancellation, checked before each entry. The kills when Core exits by itself run to the end; a stop that lands during them lets them go on for at most 250 ms more. On a timeout or cancellation, Core is first sent `SIGSTOP` (only while its start time still matches the one read when it started), so it starts no more children and its children stay its children; then a last record is made, within the same caps, until 250 ms after the stop; then Core is killed, and every recorded descendant until 500 ms after the stop; then the host waits for Core to exit until 750 ms after the stop. Each budget is checked before each entry or descendant, so the cleanup returns within 750 ms of the stop plus one `stat` read and one signal. Only Core is frozen: its descendants run until they are killed, so one whose parent exits before the last record reaches it is reparented and missed. Descendants past the caps or the budgets, and fast fork-and-exit chains between records, are missed too. .NET's `Process.Kill(true)` is not used on Linux. macOS has no `/proc`, so there only `Process.Kill(true)` on a stop applies. The .NET worker does not run in its own group (see the worker row above). | An OS-level containment mechanism, or a .NET process-group API, with its own evidence. |
| .NET SDK cache and source reads | A cache entry is verified against the file digests in its `program.json`, and every binding is derived again from Core's cached raw output, so an accidental or partial change is refused. No record inside the cache resists someone who can rewrite it: an output, its recorded digest, and the bindings changed together load. So the cache's owner is trusted and only the owner may write it: preparation refuses a cache root, an entry, or any file or directory in one that the current user does not own or that its group or others may write (read with `statx(2)` on Linux and `stat(2)` on macOS, without following links), on create and on load, and new entries are owner-only. Every symbolic link in the cache root's path is resolved once (`realpath(3)`), and the real directory is checked and used from then on; nothing inside it is followed. Every directory above the root, up to `/`, must be owned by the current user or root and must not be writable by its group or others unless it has the sticky bit (as OpenSSH checks the directories above its configuration); otherwise preparation is refused with a message naming the directory. So no other user can rename the root away and put another directory at its path. The directories a preparation makes for a missing root are each made owner-only, whatever the `umask`, but an existing parent that is group-writable only because of a `umask` of 002 (user-private groups) is refused too: run `chmod go-w` on it, or put the cache under owner-only directories. The root is used by its path, also by every worker a prepared program starts (on `<root>/<entry>/store`): its device and inode, read at the owner check, are compared again before the staging directory is made, before publishing, before and after each load, and before each worker starts, and a changed root is refused (a call then fails with a `Preparation` exception and starts no worker). Not covered: replacement by the same user or by root, whom the owner check trusts; a root renamed away and back between two comparisons, which keeps its inode (once the parents are checked, only its owner or root can rename it); and a directory above the root made writable by others after preparation, which the next preparation refuses but a prepared program does not notice (its comparisons still refuse a replaced root, except in the few system calls between the last one and a worker's start). The Core executable and every prelude file and directory are fingerprinted by path, and Core opens them by path later: each one's identity (device, inode, size, mode, owner, and modification and status-change times) is read as it is fingerprinted and compared after Core's commands finish (inside the version check and prelude discovery, before a new entry is published, and before an existing one is loaded), and any change refuses the preparation. Not detected: a file swapped and then restored with the same inode and times, which an unprivileged user can do only within the file system's timestamp granularity, since writing or renaming a file updates its status-change time (on Linux from a coarse clock, a few milliseconds); files Core loads besides the executable and prelude (its shared libraries and loader); and any change after the last comparison, since a prepared program's workers later run the executable and read the prelude (`JACQUARD_PRELUDE`) by path without checking them again. The macOS status calls are compiled but not exercised by any test. A failed preparation's cleanup removes at most 100,000 entries of its staging directory, created exclusively, and ends at a cancellation, so a stopped preparation leaves an unpublished `prepare-*` directory in the cache root; it is never loaded, and nothing removes it later (a name and an age cannot show that the SDK made a directory or that no preparation is using it), so remove leftovers yourself when no preparation is running. At most 1,024 sources are taken, refused from the list's count before any element is read, and they must be regular files totalling at most 16 MiB, the Core executable at most 512 MiB, and the prelude and cache walks read at most 100,000 entries and 256 MiB of regular files under one root, each file checked from its size before it is read and again while it is read; a source or cache file replaced by a FIFO (or, in the cache, by a link) between that check and its open can still block or redirect the open, which a cancellation does not end. | An open that cannot block on a FIFO or follow a link; directory-relative (`openat`) access pinned to the checked root; Core reading descriptors the host opened and verified. |
| .NET SDK cancellation is by token only | Preparation, Core's commands, `Call`, `Invoke`, and `MapBatches` observe the `CancellationToken` they take. `Thread.Interrupt` is not a stop signal: the SDK's own waits are `poll(2)` sleeps, which neither end at an interrupt nor consume it. The API is synchronous; there are no `Task`-returning variants. | `Task`-returning variants with the same bounds, if callers need them. |
